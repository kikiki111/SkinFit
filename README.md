# SkinFit

**新しい1本を、いつもの洗面台へ。** *Skincare that fits your life.*

売り文句に振り回されずに、あなたのお悩みから逆算した本当に必要な1本を。

ランキングも口コミも、製品ごとの評価です。あなたの洗面台にすでに何があるかまでは見ていません。SkinFitは、その手持ちから次の1本を考えるAIエージェント。

洗面台の写真から手持ちを確かめ、その全成分をGoogle検索で調べます。悩みから調べる方向性を決めて商品を探し、成分・効能表示・口コミの使用感を裏取りしたうえで、推奨1本と代替案を出します。候補を選ぶ基準は、手持ちのセット全体と、探すアイテム（化粧水・美容液など）の役割。選んだ1本を加えた朝夜の使い方まで、まとめて提示。

ここでいう「必要」は、悩み・手持ち・予算・使用感の希望から見て優先する1本という意味です。肌への効果を保証するものではありません。

第5回 Agentic AI Hackathon with Google Cloud の提出作品です。

## 写真をAIに送って聞くのと何が違うか

同じ写真をChatGPTに送って聞くこともできます。実際に比べた記録は [docs/chatgpt_comparison.md](docs/chatgpt_comparison.md) にあります（2026-10-15時点で、同じ質問を2回送った分を照合済み。残りは〔要: 比較結果〕）。

確かめた範囲では、ChatGPTの答えも、価格・効能表示・使用感はメーカーの公式ページと合っていました。差が出たのは次の3点です。

- 同じ質問で、1回目はキュレル、2回目はコラージュの化粧水を推した。2つを並べて比べる説明は無かった
- 2回目に推した化粧水の有効成分（トラネキサム酸）が、手持ちの乳液にも入っていることに触れなかった
- 1回目は、さっぱりタイプの今の化粧水を、とろみのある化粧水に替える案だった。使用感の違いは比べていなかった

SkinFitは、この部分を仕組みで扱います。

| 観点 | SkinFitの仕組み | 場所 |
|---|---|---|
| 候補の比べ方 | 候補を並べ、優先順位の高い観点から順に比べる固定の規則で順位を決める。1位と2位の差がついた観点を1文で出す | `app/ranking.py` |
| 手持ちのセット | 探すアイテムと同じ種類で「残したい」でない手持ちは入れ替える前提にし、残りのセットと比べる。手持ちのステップ × 成分の系統の表に、全成分の出典リンクを付ける | `app/routine.py`、`app/normalize.py` |
| 有効成分 | 検索本文に「有効成分」と明記されたものを取り出し、手持ちとの重なりと、入れ替えで手放すものを示す | `app/research.py`、`app/normalize.py` |
| 使用感 | 入れ替える手持ちと候補の、メーカーの使用感の説明を並べる | `app/normalize.py`、`web/app.js` |
| 値の確かさ | 全成分・価格・効能表示・有効成分は、検索で得た本文に実際に書かれている値だけを使う | `app/research.py` |

## 試し方（審査用）

1. 公開URL〔要: デプロイしたURL〕をPCかスマホのブラウザで開きます。
2. 「入力例を使う」を押し、「希望を整理する」で悩み・予算・使用感の好みを確認します。「フォームに直接入力する」から手動でも入力できます。
3. 手持ちの確認で「入力例を使う」を押します。自分の洗面台の写真を使うこともできます。
4. 「次の1本を探す」を押します。Google検索で調べるため、1〜3分ほどかかります。
5. 候補比較で根拠を開き、「ベタつきにくさ」に切り替えて、推薦と理由の変化を見ます。
6. 「手持ちと組んでみる」で、朝夜の棚の変化を確かめます。

ログインは不要です。購入手続きはアプリの対象外で、公式ページへのリンクだけを置いています。

画面だけをすぐに確認する場合は、ホームの「まずは、比較サンプルを見てみる」を使えます。実在の登録商品を表示し、検索APIは呼びません。デザイン改修とロジック点検の記録は [docs/design-audit.md](docs/design-audit.md) を参照してください。

## 仕組み

〔要: docs/architecture.png〕

| 層 | 使っているもの |
|---|---|
| 画面とAPI | FastAPI（素のHTML/JS/CSSを同じコンテナで配る） |
| 実行環境 | Cloud Run（asia-northeast1） |
| AI | Gemini 4 Argon（Vertex AI、location=global）とGoogle検索連携 |
| オーケストレーション | Google ADK 2.12 のグラフ型Workflow（JoinNodeで並行処理を合流） |
| 記録 | 標準出力のJSONログ（Cloud Logging） |

### Workflowの流れ

```
写真 → Geminiが手持ちを抽出 → 本人が確定
  ↓
[RecommendationWorkflow（ADK 2.12 のグラフ型Workflow）]
START ─┬─ owned_research          手持ちの全成分をGoogle検索で調べる（製品ごとに並行）
       └─ prepare                 調べる方向性を確定（小じわは登録済みの資料、それ以外はGoogle検索で調べる）
            ├─ dir_1 → discover_agent_1 → discover_1   探索エージェント1（ADKのAgent＋google_search）：方向性1の候補を探す
            ├─ dir_2 → discover_agent_2 → discover_2   探索エージェント2：方向性2
            └─ dir_3 → discover_agent_3 → discover_3   探索エージェント3：方向性3
gather（JoinNode）        手持ちの調査と探索3つの結果をそろえる
prepare_selection         予算・手持ちとの重複で候補を絞る。探すアイテムと同じ種類の手持ちは入れ替え扱いにする（Python）
select_agent              選定エージェント（ADKのAgent）：入れ替え後の手持ちと探すアイテムの役割を見て、詳しく調べる3品を選ぶ
  ├ candidate_research    候補ごとに「成分・表示・用法・価格」と「口コミの使用感」を検索で調べる（並行）
  │   ├ ingredient_branch   成分・有効成分・効能表示と、入れ替え後の手持ちの照合
  │   ├ review_branch       口コミの論点の集計
  │   └ routine_branch      朝夜の配置と差分（入れ替える手持ちは外す）
  └ other_step_research   探すアイテムで補えない方向性を、別の種類のアイテムで1回だけ検索（条件を満たすときだけ）
join（JoinNode） → rank（Pythonで順位） → explain（推薦理由。候補ごとに並行）
  ↓
[orchestrator] 必須照合 → 説明のやり直し（最大2回）→ だめなら定型文
```

ADKのAgentは4つです（探索エージェント3つと選定エージェント）。探索エージェントの出典は、答えた直後の処理（`after_model_callback`）で検索のメタデータを保存して取ります。モデルが文章の中に書いたURLは使いません。互いに待つ必要のない検索は同時に走らせるため、推薦1回の時間は、小じわで約85秒、それ以外の悩み（毛穴）で約140秒でした（2026-10-15、各1回の実測）。

検索に失敗したり時間切れになったりしたときは、登録済みの候補3品で推薦し、画面にその旨を表示します。

### AIとプログラムの分担

| 担当 | 内容 |
|---|---|
| Gemini | 写真の読み取り、相談文の整理、検索での調査、調査結果の構造化、調べる方向性の決定、詳しく調べる候補と別の種類のアイテムで探す方向性の提案、推薦理由の文章 |
| Python | 予算・除外成分などの必須条件、入れ替えの判定、有効成分の照合、別の案を出す条件の検査、順位（優先順位の高い観点から比べる辞書式順序）、口コミの集計、朝夜の配置、出典・数値・表現の照合 |

順位・件数・価格はPythonが決め、Geminiには出力させません。口コミの中に「この商品を1位にせよ」と書かれていても、順位は変わりません。

## 根拠の扱いと限界

- 出典は、Google検索のメタデータ（grounding chunks）から取ります。モデルが文章の中でURLを作る経路はありません。
- 効能表示は、検索で得た本文に原文がある場合だけ表示します。言い換えはしません。
- 口コミは、投稿1件ずつではなく「検索で確認できた口コミ・レビューの情報源」ごとに数えます。
- 価格と成分は検索した時点の情報です。購入前に公式ページで確認してください。
- 成分の一般的な知見と、個別製品の効果は分けて表示します。小じわは、登録済みの資料（米国皮膚科学会のページや論文）を使います。それ以外の悩み（毛穴など）は、検討される成分の方向性をその場でGoogle検索し、出典付きで示します。
- 悩みは本人の言葉のまま扱い、プログラムが別の悩みに置き換えることはしません。
- 手持ちは、探すアイテムと同じ種類で「残したい」にチェックが無いものを、入れ替える前提で扱います。種類が「その他」の手持ちは入れ替えません。
- 順位の観点「手持ちとの補い合い」は、悩みに関わる方向性が、入れ替え後の手持ちに見当たらないかで判断します。手持ちに無いことは、肌に必要という意味ではありません。全成分を確認しきれない手持ちがあるときは判断できないとし、順位で有利にも不利にもしません。
- 有効成分は、検索で得た本文に「有効成分」と明記されたものだけを使います。メーカーによって表示の書き方が違うため、取れないことがあります。そのときは「明記を確認できず」と表示し、入っていないとは言いません。
- 別の種類のアイテムの案は、候補を探す検索1回だけで作ります。価格と成分は検索本文にある値だけを残しますが、口コミと全成分の全体は調べていません。画面にもその旨を表示します。
- 「推奨」は、確認できた候補・根拠・本人の希望の範囲で優先する1本という意味です。本人への効果や刺激のなさを保証するものではありません。
- 検索結果は実行ごとに変わるため、候補の顔ぶれも変わることがあります。
- Google検索連携の表示要件に従い、結果の下にGoogle検索の検索候補を表示します。
- 商品写真は、人が公式ページで確かめた登録画像を優先します。それ以外は、商品名でYahoo!ショッピング、次に楽天市場の公式APIを検索し、商品名の語とブランド名がすべて合う単品の画像だけを出します。ショップが作った画像なので、宣伝の文字入りや近いバリエーションの画像が出ることがあります。楽天の画像は128pxと小さめです。
- Google検索連携のリンク先を開いて画像を取ることはしません。検索連携の規約が、リンク先の自動取得と結果の保存を禁じているためです。
- 検索やAPIで得た結果はサーバーに保存しません。前に調べた商品も、次の推薦で改めて調べます。検索を省けるのは、人が公式ページで確かめて登録した商品だけです（「登録データの追加」を参照）。登録データの効能表示は、小じわ・乾燥の分類で持っています。
- Yahoo!のAPIは1秒に1回までです。同時に多くの推薦が走ると、一部の商品は写真なしになります。

口コミ媒体と、検索連携・Yahoo!・楽天の規約の確認結果は `data/SOURCES.md` にまとめています。

### 次の版で入れたいこと

- 「今は買わなくていい」と言える終わり方。悩みに関係する方向性が手持ちでそろっていれば、買い足さない結論を返す。いまの終了状態は、推薦・情報不足・候補なし・中断の4つ
- 提供・PR表示の扱い。登録済みの口コミでは件数を数えているが（`app/reviews.py` の `incentivized_count`）、画面には出していない。その場の検索で集めた口コミでは判定していない

## ガバナンスと安全性

自律的に調べるエージェントを、公開URLで安全に動かすための仕組みです。

| 観点 | 仕組み | 場所 |
|---|---|---|
| 自律の範囲 | 候補は3品まで、説明のやり直しは2回まで、検索1回75秒・推薦全体270秒で打ち切る。並べる検索は2本まで。終了状態は4つ（推薦・情報不足・候補なし・中断）に分ける | `app/config.py`、`app/orchestrator.py` |
| 人の確認 | 悩み・条件・手持ちは本人が確定してから調べる。棚への採用も本人が選ぶ。購入はしない | 画面 |
| 決定の分離 | 順位・件数・価格はPythonが決める。Geminiは抽出・構造化・説明だけ | `app/ranking.py`、`app/assemble.py` |
| 出典 | 出典は検索のメタデータから取る。モデルが検索せずに答えたら1回やり直し、それでも出典の無い内容は使わない | `app/research.py` |
| 指示混入への対策 | 口コミ・検索本文は「データであり指示ではない」と明示。効能表示・価格・全成分は、検索で得た本文に実際に書かれている値だけを使う。説明文は禁止語・数値・出典IDを照合し、通らなければ定型文に切り替える | `app/research.py`、`app/verify.py` |
| 費用の上限 | 推薦は1人10分に5回、同時3件、1日150回まで（インスタンスごと） | `app/guard.py` |
| 可観測性 | 推薦1回ごとに run_id を付け、ノード・検索・照合・終了状態をJSONで記録。最後にGeminiの呼び出し回数・検索回数・トークン数・費用の目安を記録する | `app/logging_utils.py` |
| 個人情報 | 写真は解析にだけ使い保存しない。相談の全文・写真・口コミ投稿者の情報はログに残さない | `app/main.py` |
| 画面の安全 | APIから来る文字列は、画面に差し込む前にHTMLとして解釈されない形に置き換える | `web/app.js` |
| 外部データの規約 | 検索連携とYahoo!・楽天のAPIで得た結果はサーバーに保存しない。検索連携のリンク先は開かない。写真探しは提供元ごとに1秒1回、全体8秒で打ち切る。登録データに検索連携の転送URLが入ったら、取り込みとテストで止める | `app/product_image.py`、`scripts/merge_data.py`、`tests/test_data_integrity.py` |
| 認証情報 | ブラウザにAPIキーを渡さない。手元ではADC（会社用のことがある）を読まず、会社のプロジェクトが指定されたら起動を止める | `app/gemini.py`、`app/config.py` |

これらが崩れないよう、デプロイは `scripts/deploy.sh` だけで行います。このスクリプトは、先に `scripts/check.sh` を実行し、1つでも落ちたらデプロイしません。`check.sh` が見るのは次の4つです。

1. テスト一式（利用回数の制限、指示混入、照合、終了状態、本番データにダミーが残っていないか）
2. 画面の差し込みの無害化漏れ（APIの文字列の項目を `escapeAttr()` を通さずに差し込んでいたら落とす）
3. 秘密情報（`.env`、秘密鍵・APIキーらしき文字列、個人のアカウント名、`.env` に書いた写真APIのキーの値がリポジトリに入っていないか）
4. 画面のJavaScriptの構文

限界もあります。指示の文が数字ごとページに書かれていると、「本文に書かれた値だけを使う」確認では防げません。その場合も、順位をPythonが決め、予算の条件で絞り込み、価格に出典へのリンクを付けることで影響を抑えます。利用回数の記録はインスタンスのメモリに持つため、実質の上限はインスタンス数の倍になります。

## 手元での起動

前提は、uv と gcloud（個人アカウントでログイン済み）と、Vertex AIが有効なGCPプロジェクトです。

1. `.env.example` を `.env` に写し、`SKINFIT_GCLOUD_ACCOUNT` に個人のgcloudアカウントを書きます。
2. 商品写真を出すときは、`SKINFIT_YAHOO_CLIENT_ID`（Yahoo!デベロッパーネットワークのClient ID）と、`SKINFIT_RAKUTEN_APP_ID`・`SKINFIT_RAKUTEN_ACCESS_KEY`（楽天ウェブサービスのアプリIDとアクセスキー）も書きます。空なら写真なしで動きます。
3. `./scripts/dev.sh` を実行します。表示されたURLを、MacのブラウザとiPhoneのSafari（同じWi-Fi）で開けます。

手元ではADC（application_default_credentials.json）を読まず、`gcloud auth print-access-token` のトークンを使います。Cloud Run上ではサービスアカウントを使います。

## 登録データの追加（検索を省く商品）

手持ちや候補が登録商品に一致すると、その商品はGoogle検索を省いて登録データを使います。品名は、製品名か別の書き方（`name_aliases`）と照合します。登録の手順は次のとおりです。

1. メーカー公式の製品ページを人が選び、下書きを作ります。例: `uv run python scripts/draft_product.py --url <公式ページのURL> --role owned --alias "とてもしっとり 化粧水"`
2. `data/drafts/pending/` にできた下書きを、公式ページと見比べます。全成分・価格・効能表示・画像URLを確かめます。
3. 確かめた下書きを、`data/drafts/owned.json`（手持ち）か `data/drafts/candidates.json`（候補）の配列へ移します。
4. `uv run python scripts/merge_data.py` で `data/products.json` へ取り込みます。

Google検索連携で調べた結果は、登録データに写しません。検索連携の規約が、結果の保存とデータベース化を禁じているためです。下書きツールは人が選んだページを直接読み、構造化のGeminiにも検索ツールを付けません。画像はダウンロードせず、公式ページの画像URLだけを持ちます。

取り込みとテストは、検索連携の転送URL（`vertexaisearch.cloud.google.com`）を含むデータを止めます。下書きに無いデータが `data/` から消える場合も止まります。消すつもりのときだけ `--allow-removal` を付けます。新しく登録した商品は、検索に失敗したときの代替候補には入りません。代替に使うのは `demo_role` の付いた3商品だけです。

## 検証の記録

企画書§11の項目ごとに、確認した方法と結果を記録します（2026-10-15時点）。テストは `uv run pytest` で135件が通過し、Geminiを呼ぶ1件は `SKINFIT_LIVE=1` のときだけ実行します。画面のテストは `npm test` で30件が通過しています。

| 確認項目 | 方法 | 結果 |
|---|---|---|
| 悩み・使用感・予算・必須条件を区別する | 相談文の整理（`/api/intake/parse`）を実際のGeminiで実行 | 悩み・予算・使用感の好み・残したい商品が別の欄に入った。本人が明示しない限り「使用感の根拠を必須」にしないよう指示文を修正した |

# SkinFit デザイン改修・ロジック点検

実施日：2026-10-15

## 画面

明るいアイボリーにピーチとローズを合わせ、明朝の見出し、細い罫線、余白を中心とした美容誌のような画面に刷新。初回のオリーブ配色から、ユーザーのフィードバックを受けて華やかさのある暖色へ調整。スマホで相談、手持ち確認、比較、朝夜の使い方まで進められる構成にした。

- ホーム：実物の写真を使った商品ビジュアル、自然文の相談、直接入力できるフォーム。
- 商品比較：推奨商品と代替候補、比較表、使用感の内訳図。結論を先に、詳しい根拠は開閉式で表示。
- 使い方：朝・夜の順序図、「いまの組み合わせ」と「1本を加えると」の比較。時間帯を確認できない商品は別枠に表示。
- 調査中：工程表示、中止、失敗時の復帰。並べ替えに失敗しても前の結果を保持。
- 比較サンプル：`GET /api/preview`。実在の登録商品を使用し、新たな検索や口コミの生成はしない。サンプルであることを明示。

商品写真は、メーカー公式の画像ファイルをリポジトリに置かない（公式サイトの規約で複製・転載を禁じているため）。写真は登録データの公式画像URLか、Yahoo!・楽天の公式APIで照合した画像だけを表示し、どちらもなければ写真未確認の表示にする。ホームの見本はCSSで描いたボトルにした。

## 修正したロジック

| 問題 | 修正後 |
| --- | --- |
| 除外成分があるのに全成分不明の商品を通せる | 全成分を確認できない場合は除外判定ができない理由を示し、候補から外す |
| 成分の別名照合に別のカタログが使われる | リクエストで使うカタログの別名を使う。「アルコール」と「エタノール」を対応付ける |
| 手持ちの全成分が不明でも「新しい方向性」と判断 | 未確認として分ける |
| 順位付け前に4件目以降を落とす | 適合する全候補を順位付け対象にする |
| 同点でも口コミ件数に差があるように説明 | 完全同点と情報量の差を区別する |
| 希望がなくてもベタつきを優先する | 通常は希望された場合だけ順位の観点に含める |
| 再順位付け後に以前の順位を前提とした説明が残る | 新しい順位から定型説明を作り直す |
| 時間帯不明の商品を朝夜両方に配置 | 未配置として残す。夜のみの商品は差分表示も夜のみ |
| 組み合わせの選択が元の手持ちを変える | 選択状態と元のルーティンを分離する |
| 1,100円の一部を100円として確認できる | 通貨表記の金額全体を照合する |
| 指定された出典がなくても別の出典を充てる | 有効な出典参照がない効能・価格・成分・用法を採用しない |
| 説明生成まで含めると処理時間の上限を超える | リクエスト全体のタイムアウトを追加する |
| 結果なしで通信が終わると待機画面が残る | エラーとして入力画面へ復帰する |
| 古い通信結果が現在の画面を上書きする | 中止信号とリクエスト識別で古い更新を抑止する |
| 不正な予算・空の商品名・過剰な手持ち件数 | APIと画面で検証。再順位付けの不正データは422で返す |

動的な文字列はHTMLエスケープし、外部リンクはHTTP(S)に制限。検索候補のHTMLは制限付きiframeに分離した。既存の簡易エスケープ検査も新しい関数名に合わせて更新した。

## 残る制約

- 新しい実検索を含むGemini / Vertex AIの一連の動作と、Cloud Runへのデプロイは今回実施していない。
- 公式写真を保存したのは3商品。その他の商品は、後述「検索で見つけた商品の写真」の方式で、公式APIの照合済み画像だけを使う。詰替版や別の商品の写真を推測で関連付けない。
- 順位は確認できた製品情報に基づく規則であり、個人の肌との適合性を臨床的に予測するものではない。悩みの分類や成分群の照合には引き続き限界がある。
- 用法の時間帯を確認しても、図の順序はカテゴリによる目安。個別製品の細かな用法や併用可否を自動で判定していない。
- 香り・なじみ等の希望は整理して表示するが、現在の順位計算の使用感観点はベタつき。画面にもその範囲を記載している。
- 出典参照の存在と本文との照合を行っても、検索結果の誤り、製品の世代・地域差、各主張を出典が十分に裏付けるかまでは保証できない。
- 再順位付けはクライアントから渡された分析データを再計算する。サーバーに署名付きの調査記録を保存する仕組みではない。
- 組み合わせの選択はこのページ内だけの状態。リロード後の保存や購入機能はない。

既存のレート制限・利用量記録等の変更は維持。コミットや公開環境の変更は行っていない。


## 縦型フローへの変更（2026-10-15）

- 横並びのステップ移動を廃止し、希望・手持ち・商品比較・使い方を同じページで下に展開する。完了した工程は要約に折りたたみ、未到達の工程は表示しない。
- 編集中は後続工程を隠す。取り消しでは入力と選択を復元する。同じ内容を再確定した場合は結果を再利用し、変更した場合は古い結果を無効化する。希望を変えても手持ち入力は保持する。
- 調査中は要約からの編集を停止。中止・通信失敗時は入力を保持して復帰する。進捗と結果は同じ位置に表示し、完了時にフォーカスを移動しない。
- 比較サンプルでは未入力を確認済みと表示しない。進む矢印は下向き、前の工程を開く矢印は上向きに統一した。
- API・推薦ロジックに変更なし。動きを減らす設定ではスクロールを即時移動にし、見出しのフォーカスと開閉状態のアクセシビリティ属性を追加した。
- JavaScriptの回帰テストを18件に拡充。工程の可視性、入力変更時の無効化、変更なしの再利用、取り消し、遅れて届く解析結果、中止、フォーカス、動きを減らす設定を検証する。

- 最終確認：Python 72 passed / 1 skipped、JavaScript 18 passed。書式・構文・簡易エスケープ検査も成功。
- 実ブラウザ：320・390・768・1280pxで4工程の縦配置と横はみ出しなしを確認。入力の整理、直接入力、再編集、取り消し、再利用、条件変更、中止、通信中断後の再試行、フォーカス維持を検証した。
- 動きを減らす設定はJavaScriptの分岐を自動テストで検証し、対応CSSも維持。OS設定を変更した実ブラウザ検証は行っていない。独立したPlaywrightスクリプトには設定切替の検証を追加したが、そのスクリプト自体は未実行。


### 前へ進むと画面が上へ戻る挙動の修正

原因は、スクロール前に前工程を折りたたみ、移動先の見出しが現在位置より上へ移っていたこと。前工程の高さを保ったまま次へスクロールし、到着後に折りたたむ方式へ変更した。折りたたみで減った高さを即時補正し、移動先の画面内位置を保つ。移動中の前工程は操作できない状態にし、手動でスクロールを中断した場合は到着前に折りたたまない。高速な調査完了で進捗が結果に変わっても、移動を継続する。

この3ケースの回帰テストを追加し、JavaScript 21件が通過。スマホとPCの実画面で、移動中は前工程が展開されたまま、到着後は見出しが画面上部の約52pxに留まることを確認。


## 検索で見つけた商品の写真と、登録商品で検索を省く仕組み（2026-10-15）

### 写真がいつも出なかった原因

写真の関連付けは、保存した3商品（`web/assets/products/manifest.json`）とブランド名・商品名が完全に一致したときだけだった。推薦はその場の検索で商品を探すため、3商品以外はすべて「商品写真は未確認です」になっていた。

### 検討して採らなかった案

- 出典ページの og:image を読む案と、調べた成分・商品名を Cloud Storage に保存して次回に使う案は採らない。Google Cloud Service Specific Terms §20(k)(i) が、検索連携の結果のキャッシュ・保存・データベース化と、リンクを使って取得先ページを特定しクロール・スクレイピングすることを禁じているため。
- Amazon は、旧API（PA-API 5）が廃止され403を返す。robots.txt もボットを禁じている。

### 変更内容

- 写真の順番を「登録画像 → Yahoo!ショッピング商品検索API（600px）→ 楽天商品検索API（128px）」にした（`app/product_image.py`）。商品名の語とブランド名がすべて商品タイトルに含まれ、セット・詰替・お試しでない出品だけを採る。写真探しは検索と並行で走り、全体8秒で打ち切る。Yahoo!の上限に合わせ、提供元ごとに1秒1回の間隔を空ける。
- 写真の枠には提供元へのリンク（「Yahoo!ショッピングで見る」「楽天市場で見る」）だけを置く。「公式の商品ページ」と書くのは登録画像のときだけ。画面下部に各社指定のクレジットを置いた。外部画像が読めないときは写真なしの表示に戻す。
- 手持ち・候補が登録商品（`name_aliases` の別表記を含む）に一致したら、Google検索を省いて登録データを使う。候補の口コミは、ほかの候補と数え方をそろえるため検索を続ける。代替候補は `demo_role` の付いた3商品に限った。
- 登録データの下書きツール `scripts/draft_product.py` を追加した。人が選んだ公式ページを直接読み、その場の調査と同じ構造化と照合で下書きを作る。画像はURLだけを持つ。
- `scripts/merge_data.py` に2つの検査を足した。検索連携の転送URLを含む下書きと、下書きに無い既存データが消える取り込みを止める。後者は、古い `data/drafts/ingredient_aliases.json` で本番の別名9件が消えるのを実際に止めた。

### 確認結果

- Python：`uv run pytest -q` → 120 passed, 1 skipped。写真探し（照合・提供元の切り替え・429・時間切れ・間隔）、登録商品での検索省略、下書きツール、取り込みの検査を追加。
- JavaScript：`npm test` → 24 passed。https画像の表示、http・javascript・data の拒否、楽天の枠のリンク、リンク表記の切り替えを追加。
- Yahoo!・楽天のキーを使った実通信、実際の推薦での写真の表示率、ブラウザでの表示は未確認（キーの発行後に確認する）。

### 残る制約

- ショップが作った画像なので、宣伝の文字入りや近いバリエーションの画像が出ることがある。
- 規約上、検索とAPIの結果は保存できない。速くなるのは登録した商品だけで、登録はまだ3商品。
- 楽天規約の「APIを使った部分」の範囲は、写真の枠と解釈した。Yahoo!のAPIで得たデータを保存してよいかは確認できていないため、保存しない。
- 検索連携の結果をGeminiで構造化して表示する既存の処理と、同規約(4.1)「結果を改変しない」の関係は未確認。
